## Project Snapshot

riff is a self-hosted PocketBase backend serving memos, patches, samples, and spaces for PO-33 sampler creators.

- Backend: Go 1.27.0, PocketBase v0.40.5, Connect RPC, gRPC-Gateway, Protocol Buffers. The Go binary is `main.go` at the repo root (no `cmd/`).
- Frontend: React 19, TypeScript 7, Vite 8, Tailwind CSS v4, React Query v5. The Memos SPA is built by `pnpm release` (Vite) into `server/frontend/dist/` and embedded into the riff binary at compile time via `//go:embed` in `server/frontend/embed.go`. PocketBase serves it at `/` (with `/_/` reserved for the admin UI).
- Storage: PocketBase owns the DB layer (SQLite by default). There is no per-driver SQL; collections are defined in `pb/migrations/*.go` and registered via a blank import from `main.go`.
- Generated API outputs: `proto/gen/` for Go/OpenAPI, `web/src/types/proto/` for TypeScript.
- Module path: `github.com/incurl/riff`.

## Working Rules

- Read relevant code before editing; prefer local patterns over new abstractions.
- Keep diffs scoped. Do not do repo-wide cleanup, dependency churn, or generated-file rewrites unless the task requires it.
- Do not hand-edit generated proto outputs. Change `.proto` files, then run `buf generate` from `proto/`.
- New collections go in `pb/migrations/` as a Go migration that calls `migrations.Register(...)` in an `init()`. The blank import in `main.go` makes the collection discoverable to PocketBase's migrate plugin.
- Public Connect/gRPC endpoints live in `pb/connect/`; custom REST endpoints live in `pb/api/`. PocketBase collection access rules (in the migration) and the `Route` ACLs in those packages together govern who can call what — do not add an endpoint without checking both.
- MCP tool visibility comes from `proto/gen/openapi.yaml`. Add a new endpoint by registering the Connect handler and regenerating OpenAPI; the MCP service picks it up on next start.
- Ask before adding heavy dependencies, changing auth/token behavior, or altering Docker/release workflows.

## Commands

Run from the repository root unless a command starts with `cd`.

On this workstation the toolchain binaries are outside the default PATH of
non-interactive shells: `node` and `pnpm` live in `~/.local/bin` (and `pnpm`
must run under *that* Node — the v20 on `PATH` dies with
`No such built-in module: node:sqlite`), while `buf` and `golangci-lint` live
in `~/go/bin`. Prefix the command rather than relying on the interactive
shell: `PATH="$HOME/.local/bin:$PATH" pnpm test`,
`PATH="$HOME/go/bin:$PATH" golangci-lint run`, or, from `proto/`,
`PATH="$HOME/go/bin:$PWD/../web/node_modules/.bin:$PATH" buf generate`.

```bash
# Backend
go run -buildvcs=true . serve                    # Serve (CalVer derived from HEAD commit date; `serve` is required — the root command only prints help)
go test ./...                                    # All Go tests
go test -v -race ./pb/connect/ ./pb/hooks/       # Race detector on the hot path
go test -v -race ./internal/...                  # Internal package tests with race detector
go test -v -race ./server/mcp/                   # MCP service tests with race detector
go test -v -run TestFoo ./pb/...                 # Run matching Go tests in one tree
go mod tidy -go=1.27.0                           # Match CI tidy check
golangci-lint run                                # Lint (config: .golangci.yaml, includes depguard layering)
golangci-lint run --fix                          # Auto-fix lint, including goimports

# Frontend
cd web && pnpm install             # Install dependencies
cd web && pnpm dev                 # Dev server on :3001; proxies /api, /api/v1/sse, /memos.api.v1, /file to DEV_PROXY_SERVER (default http://localhost:8090, i.e. the riff backend)
cd web && DEV_PROXY_SERVER=http://riff.internal:9000 pnpm dev   # Dev against a backend on a different host/port
cd web && pnpm lint                # Type check + Biome lint
cd web && pnpm test                # Vitest unit tests (requires Node 24+; see web/.nvmrc and the Frontend Conventions)
cd web && pnpm build               # Production build
cd web && pnpm release             # Build SPA into server/frontend/dist (//go:embed bakes it into the binary)

# Protocol Buffers
cd proto && buf generate           # Regenerate Go + TypeScript + OpenAPI
                                   # (needs `protoc-gen-es` on PATH: run
                                   #  `cd web && pnpm install` first, or
                                   #  export PATH="$PWD/web/node_modules/.bin:$PATH")
cd proto && buf lint               # Lint proto files
cd proto && buf format -w          # Format proto files
```

Layering rules, enforced by `depguard` in `.golangci.yaml`:

- Imports point downward only: `main.go` → `pb/` → `server/` → `markdown/`, `internal/`. The `server/mcp/` and `pb/*` packages live at the same level; treat them as siblings, not as a chain.
- `internal/` packages import nothing from this module (except `internal/testutil`, which may import `proto/gen`).
- A package goes in `internal/` only if it could be published as a standalone module unchanged. If it knows what a Memo, Space, or instance setting is, it is a root package.
- Never create `util`, `common`, `base`, `helpers`, `misc`, or `pkg` packages. Name a package for the one thing it does, or put the code next to its only caller.
- New business rules extracted from a handler go to a sibling subpackage, e.g. `pb/connect/feed/` for feed-specific logic. Keep `pb/connect/<resource>_service.go` thin.

File convention inside `pb/connect/`: `<resource>_service.go` holds the RPC handlers, `<resource>_service_converters.go` the
store↔proto conversion, and `<resource>_service_<topic>.go` further splits. Extend the matching file; do not add `*_helpers2.go`.
Tests live next to the code (`*_test.go`) or in the same package's `*_test.go` black-box style.

| CEL `filter` on `ListMemos` / `ListAttachments` | `internal/cel/` (the compiler) plus `pb/connect/cel_fields.go` (the per-collection field schema, the space-name rewriter and the `state` clause). Both handlers used to pass `""` as the PocketBase filter, so **every** SPA filter — space, creator, tag, content search, visibility, calendar range, pinned, saved views — returned the unfiltered feed. The compiler targets PocketBase's own filter grammar (parsed by `fexpr`), **not SQL**: operands may not be parenthesised, there is no arithmetic the query can carry (only `now ± duration(...)` is folded at compile time), no `!` (negation is pushed down by De Morgan in `negate`), and only `geoDistance`/`strftime` exist as functions. `has_link` and friends compile to dotted JSON paths (`payload.property.has_link = true`) because PocketBase resolves those itself — `json_extract(...)` is not a filter function. Timestamps bind the **TEXT** form `"2006-01-02 15:04:05.000Z"` (`tools/types.DefaultDateLayout`), not an epoch, or every calendar filter returns nothing (and `timestamp()` accepts both CEL forms — an RFC 3339 string and Unix seconds — because `web/src/lib/calendar-utils.ts` builds `timestamp(1749340800)` while saved views spell the string form). `?= ` only resolves on relations, so JSON-array membership (`tags`) expands to four anchored LIKE patterns in `jsonListMember` — a bare `tags ~ '"work"'` also matches `"workout"`. Anything the grammar cannot express (`content.matches`, `size(x)` other than `== 0` on a list field, `sets.equivalent`, `tags.all`, arithmetic other than `now ± duration(...)`, a non-equality `tags.exists(e, …)`) is a `CodeInvalidArgument`, **not** a silent unfiltered feed. The documented spellings that *are* expressible must keep compiling: `"work" in tags`, `tag == "work"` (the spelling older saved views carry), `tags.exists(t, t == "work")`, `now - duration("168h")` (folded into a bound timestamp by `parseAddSub`), `<field>.contains(…)` for any registered scalar field, `<field>.startsWith(…)` / `<field>.endsWith(…)` (all three differ only in the wildcard padding `likeWildcards` applies, so they share the `~` operator and `negate` flips `~` to `!~` for all of them), `size(tags) == 0`, a bare `true`/`false` (`id != ""` / `id = ""`), and `!has_location` via `Field.NegatedExpr`. **The string matches depend on one PocketBase behaviour**: `wrapLikeParams` (tools/search/filter.go) escapes a bound value and wraps it in `%…%` only when the value carries no unescaped `%`, so a pre-padded pattern passes through verbatim — that is what makes `"a%"` mean *starts with* rather than *contains*, and `TestListMemos_StringMatchFilters` fails if a PocketBase upgrade changes it. The compiler escapes the caller's own `%` and `_` (an existing `\` escape is left alone), which also fixes a latent bug: `contains("100%")` used to bind the raw value, PocketBase skipped its wrapping, and the query became a *prefix* match on a literal percent sign. `attachments.creator` uses `Field.FallbackColumn`/`FallbackWhen` because the `creator` column is only stamped on orphan uploads: `creator == …` compiles to `((memo.author = x) || ((creator = x) && (memo = null)))`. **A filter is bounded twice**, because every term compiles to its own clause and the recursive descent has no other recursion than grouping and negation: `maxFilterLength` (8 KiB, mirroring upstream's `ParserExpressionSizeLimit`) is checked in `Compile`, and `maxParseDepth` (256) is enforced by `parser.enter`/`leave` in `parsePrimary`'s group and `parseNot`. Without them a 256 KB filter took **7.16s** to compile and a 1.6 MB one was **OOM-killed**; both now fail in microseconds. The depth guard is a *path* limit, not a total, so sibling groups reuse the counter. Note the two guards can mask each other in a test — 200k nested parens is 200 KB and trips the length guard first — so `TestCompile_LengthAndDepthGuardsAreIndependent` pins that both are reachable. A saved-view write compiles its filter too (`pb/connect/memo_views.go::validateMemoViewFilter`), so `CreateMemoView(validate_only: true)` rejects a filter the feed would 400 on, and `web/src/pages/MemoViews.tsx`'s example list is limited to the compilable subset on purpose. Two producers outside `pb/connect` must therefore emit CEL: `pb/api/upstream_memos_v0_convert.go` (`pinned == true`, not `pinned = true`) and `v0ResolveMemoName`, which must **not** forward the request query string to `ListMemos` — a PATCH/organizer call carries `?pinned=true` from an earlier list, and an unpinned memo then drops out of the id lookup and 404s. | `go test -count=1 ./internal/cel/` and `go test -count=1 -run 'TestListMemos_\|TestListAttachments_\|TestCELIdentityRewriter\|TestMemoStateFilter\|TestMemoView_ValidatesFilter' ./pb/connect/`. `pb/api` must be re-run too: `go test -count=1 -run TestV0 ./pb/api/` — `TestV0PatPath_MoeMemosBoot` is what caught the V0 shaper's non-CEL filter, and the V0 surface is the riskiest possible thing to break. |

## Go Conventions

- Wrap errors with `errors.Wrap(err, "context")` from `github.com/pkg/errors`; do not use `fmt.Errorf`.
- Return Connect/gRPC errors with `connect.NewError(connect.CodeX, ...)`. Reserve `status.Errorf` for the rare case where a handler returns a code from `google.golang.org/genproto/googleapis/rpc/errdetails` directly.
- Keep imports grouped as stdlib, third-party, then `github.com/incurl/riff/...`; goimports is run by golangci-lint.
- Add doc comments for exported identifiers; godot enforces exported comment punctuation.
- Avoid package-level mutable state unless the surrounding package already uses that pattern. PocketBase record hooks are a deliberate exception: `pb/hooks/` registers once on `app.OnServe().BindFunc`.

## Frontend Conventions

- Use `@/` for absolute imports.
- Follow Biome formatting: 2-space indent, double quotes, semicolons, 140-character line width.
- Put server data in React Query hooks under `web/src/hooks/`; keep UI-only state in contexts or component state.
- Copied/shareable URLs must be absolute. Build them from `profile.instanceUrl` when set (it already carries any sub-path and the router path is concatenated verbatim, so that path must start with `/`), otherwise from `window.location.origin` plus `withBasePath` / `BASE_URL`. `MemoDetailSidebar.tsx` and `MemoActionMenu/hooks.ts` are the reference implementations; a missing leading slash produced `https://hostmemos/{id}` when `instanceUrl` was configured.
- Use Tailwind CSS v4 utilities, `cn()` for class merging, and CVA for variants.
- Reuse Base UI primitives and existing components before adding new UI primitives.
- Keep generated proto TypeScript under `web/src/types/proto/` out of manual edits and Biome rewrites.
- The test runner requires Node 24+ (matches `web/package.json` `engines.node` and `web/.nvmrc`). `pnpm test` runs a `pretest` guard that aborts with a clear message on older Node — `nvm use` (or `fnm use` / `volta run pnpm test`) is the supported path to the right version.

## Database And Proto Rules

- Schema changes are a new Go migration in `pb/migrations/`. PocketBase applies them on the next `app.Bootstrap()` run; the migratecmd plugin handles this automatically.
- Migrations must be **idempotent across fresh installs and existing instances**: do not assume an empty schema, and do not destroy user data when adding optional columns.
- Proto field changes must preserve compatibility unless the task explicitly allows a breaking API change. New RPCs and fields go through `proto/api/v1/`; the generated OpenAPI is the MCP surface.
- Regenerate after proto edits with `cd proto && buf generate` and include both Go/OpenAPI and TypeScript generated outputs in the same commit.

## Verification Policy

- Run the narrowest relevant checks while iterating.
- Before finishing, run the checks that match the changed surface from "Change Routing".
- For docs-only changes, `git diff --check` is sufficient unless the docs include runnable examples that should be tested.
- If a required check cannot run locally, report the reason and the exact command that remains.

## Known Issues (post-refactor)

These are tracked in the commit message of `3bd5c81d` and are not blocking the
rest of the test suite, but are worth flagging before any release:

1. **`main.go` previously passed `&profile.Profile{}` (zero value) to `mcp.Register`**, so
   the origin allow-list matched nothing. Fixed in Phase 5 Slice D:
   `buildProfileFromEnv` reads `RIFF_INSTANCE_URL` and threads the real
   value into both `mcp.Register` and `hooks.InstallEmailDispatcher`.

The `pb/hooks/memo_links.go::memoLinksFanOut` worker-pool race (item 1 in the
prior list) is fixed in the same commit as the user-webhook lifecycle: the
goroutine honours a per-app `memoLinksShutdown` channel that the OnTerminate
hook closes, and both `pruneStaleMemoLinks` and the per-URL worker pool have
a `recover()` wrapper so a closed-DB panic during a test app cleanup does
not crash the runner. `upsertMemoLinkRow` returns `(nil, false)` when the
`memo_links` collection is absent so the worker can short-circuit before
hitting the nil-deref that an earlier version tripped over. The two new
`TestUpsertMemoLinkRow_MissingCollection` and
`TestUpsertOneMemoLink_MissingCollection` tests pin the regression.

A second, related class of teardown race was fixed alongside the
attachment work (2026-10-20): the detached goroutines in
`pb/hooks/motion_media.go`, `pb/hooks/memo_links.go`,
`pb/hooks/scheduler.go`, `pb/hooks/webhook_drain.go`,
`pb/connect/upload_session.go` and
`pb/connect/memo_import_session.go` were not tracked, so the app
could tear its data directory down while one of them was still
writing into it. In a test that surfaced as
`TempDir RemoveAll cleanup: directory not empty` — and, because the
goroutine belonged to a *different* test, the failure landed on an
unrelated test, which made it very hard to attribute.

All six now track their goroutines in a `sync.WaitGroup` that the
app waits on during teardown. Three details are load-bearing:

* The wait is bound to **`OnBootstrapClear`**, not
  `OnTerminate`. A test's cleanup calls `app.ClearBootstrap()`,
  which triggers `OnBootstrapClear` but NOT `OnTerminate`, so a
  wait on the latter never runs in a test — and the test is
  exactly where the teardown race bites.
* The stop signal is sent **before** the wait. The wait blocks
  until the worker returns, and the worker only returns after it
  observes the signal; waiting first deadlocks the teardown.
* The scheduler's shutdown channel is **closed**, not sent on. An
  unbuffered send with a `default:` branch is silently dropped
  unless the worker happens to be parked in its `select` at that
  exact moment — which left the loop waiting for its 1-minute
  tick. A closed channel is seen by every future select.
* The wait group and the shutdown channel are **per app**, not
  package-level. A `sync.WaitGroup` cannot be waited on twice
  concurrently, so two apps tearing down at the same time panic
  with "sync: WaitGroup is reused before previous Wait has
  returned"; and a package-level channel closed for one app stops
  every other app's worker. The per-app state lives on the
  app's own `app.Store()` (PocketBase's per-app key-value
  store), so it is per app by construction and dies with the
  app instance. Note that the race detector cannot see this class
  of bug — the misuse is a runtime `panic()`, not a data race.

The symptom is gone: six consecutive full runs of
`./pb/ ./pb/migrations/ ./pb/api/` are clean, where the flake
previously hit roughly one run in six.

### The PocketBase logger teardown race is a *different* bug

The fix above covers riff's own detached goroutines. It does **not** cover
PocketBase's log writer, which is the remaining source of both symptoms,
and it is worth naming because the two look identical in the output:

* under `-race`, a DATA RACE between `ClearBootstrap` nil-ing
  `app.concurrentDB` (`core/base.go:506`) and the logger's flush goroutine
  reading the same field in `createTxApp` (`core/db_tx.go:53`);
* in long runs, `TempDir RemoveAll cleanup: directory not empty`.

`core.initLogger` runs a 3-second `time.Ticker` and a 200-entry
`BatchHandler`; on each flush `WriteFunc` hands the batch to
`routine.FireAndForget(runLogsWrite)`, which opens an **aux** DB
transaction. The `OnBootstrapClear` hook (priority -999) flushes what is
already queued and signals the ticker, but a tick that has *already fired*
hands its batch to a goroutine nobody joins. That goroutine then reads the
DB handles concurrently with the write `ClearBootstrap` performs, and — in
the window between the test body returning and the temp dir being removed —
writes into a directory that is being deleted.

**Every `core.NewBaseApp` in a test must therefore call
`testutil.DisableLogPersistence(app)` immediately after `Bootstrap()`**
(`internal/testutil/pocketbase.go`). It sets
`app.Settings().Logs.MaxDays = 0`, which shuts the writer off at the
source: `BeforeAddFunc` returns false for every record, so nothing is
queued, `BatchHandler.WriteAll` short-circuits on an empty batch and never
reaches `WriteFunc`, and `runLogsWrite`'s own `MaxDays == 0` guard makes a
tick already in flight a no-op. Two orderings matter: settings are loaded
during `Bootstrap()`, so a mutation made before it is discarded, and the
call has to happen before any test logs anything.

No test asserts on persisted log rows, so the only behaviour change is that
`logs.db` stays empty under test. Production is untouched — `main.go` never
calls this. See DECISIONS.md "`Logs.MaxDays = 0` in tests: the teardown
race".

## CI Reference

- Releases are cut by pushing a `YY.MM[.N][-rc.N]` tag. To cut, promote, or check a release, follow
  `.agents/skills/release/SKILL.md` (currently still Memos-shaped; needs a riff-specific rewrite before the first riff release).
- Development builds use the HEAD committer date in UTC as `YY.MM`; release builds inject the CalVer tag.
- `go build` embeds Git metadata automatically; `go run` needs `-buildvcs=true`. Builds without Git metadata must inject
  `github.com/incurl/riff/internal/version.Version` through `-ldflags`.
- Docker excludes `.git`; pass `--build-arg VERSION="$(bash scripts/release_version.sh development-version)"` and
  `--build-arg COMMIT="$(git rev-parse HEAD)"` when building locally (build frontend assets first). The
  `scripts/Dockerfile` builds `./` (the repo root, where `main.go` lives) and produces a single image with
  caddy+supervisord+riff on Alpine 3.21, exposing ports 80+443. The buildkit named context `ravine` must be
  passed too (`--build-context ravine="$(readlink -f scripts/ravine)"`); the static site lives outside this repo
  and the symlink is only a pointer. Companion `fly.toml` is the Fly.io deployment manifest: the default
  `scripts/Caddyfile` serves riff behind a `/community/*` prefix, but `fly.toml` sets `CADDYFILE=Caddyfile.fly`
  so the SPA answers at the root of the assigned hostname, and it is `internal_port = 80` so the Fly proxy points
  at caddy, not at riff. caddy is launched with an explicit `--adapter caddyfile`, which a non-default `CADDYFILE`
  value requires (caddy only auto-detects the adapter from a base name of exactly `Caddyfile`). Build the image
  locally (`-t riff:dev --load`), push it to the Fly registry, then deploy that pushed reference:
  `flyctl auth docker && docker tag riff:dev registry.fly.io/ravine:dev && docker push registry.fly.io/ravine:dev
  && flyctl deploy -a ravine`. `fly deploy --image` resolves the reference on the Fly side and never uploads a
  local-only tag (it fails with `Could not find image "docker.io/library/riff:dev"`), which is why the image must
  be pushed first; the same `--build-context ravine=...` must be passed to `docker buildx`.

- Backend CI: Go 1.27.0, `go mod tidy -go=1.27.0`, golangci-lint v2.13.1, test groups `pb`, `server`, `internal`, `other`
  (`markdown`, `proto`).
- Frontend CI: Node 24, pnpm 11.0.1, `pnpm lint`, `pnpm test`, `pnpm build`.
- Proto CI: `buf lint` and `buf format` check.
- Docker: `scripts/Dockerfile`, Alpine 3.21 runtime, caddy+supervisord+riff, **ports 80+443** at the public surface (riff's PocketBase 8090 stays on the loopback; caddy reverse-proxies `/community/*`), multi-arch amd64/arm64/arm/v7.
